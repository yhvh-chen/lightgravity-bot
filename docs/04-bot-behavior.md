# Bot 行为与交互契约

> 日期：2026-10-14。阶段：设计。本文补齐常驻 Bot 的消息与资源生命周期，不代表服务已经运行。首版采用单用户网页入口，外部聊天渠道、自主触发与多用户组织暂缓。

## 1. 常驻 Bot 与临时执行

常驻的是服务、消息入口、协调器与持久任务队列，不是一直占用模型的 SDK 会话。空闲时不做模型轮询；新消息到达后按需调用模型。默认不存在独立常驻编排模型：交付 Run 由程序按明确目标生成最小合法计划并直接派发，模型拆解是可选的有界按需能力，不是每次 Task/Run 的前置。临时 worker 完成、暂停、失败或取消后，确认停止并关闭会话，留下恢复记录与产物。

Bot 在同一身份下接收指令、回答问题、维护 Task 上下文和汇报执行结果。用户不必了解 Run、SDK session 或资源配置文件即可使用。

## 2. 消息分类与路由

每条消息先持久保存，再由确定性控制指令和必要的模型意图判断路由。Task 选择和执行操作须校验，不直接执行模型提出的任意动作。

| 意图 | 行为 | 是否需要 Task/Run |
|---|---|---|
| 普通问答、能力介绍 | 直接回复，不组队 | 全局会话，无 Run |
| 简单资料读取或一次搜索 | 获准工具在有界单 agent 会话内处理 | 全局或已有 Task，无交付 Run |
| 新交付需求 | 创建 Task，保存目标、范围和验收；输入充分且属于获准范围时进入队列 | 新 Task，执行时创建 Run |
| 当前任务的说明、补资料 | 保存到 Task，必要时更新需求版本 | 保留 Task；不自动新建 Run |
| 继续、重试、返修 | 选择 checkpoint 恢复或创建新执行尝试 | 保留 Task，关联 Run |
| 状态、队列、成本、结果查询 | 读取持久状态与证据，不启动 worker | 无新 Run |
| 暂停、取消 | 控制目标执行，确认真实状态后汇报 | 无新 Run |
| 验收、拒绝、重新打开 | 绑定交付版本与明确决定，校验有效性 | 更新已有 Task |
| 上传资料、粘贴链接、未来文件夹/邮箱接入 | 进入受控摄取作业：先落盘，再提取/归属/索引，并按文件回执 | 受控收件区；全局上传不强建 Task，可靠时归入当前 Task/Project |

在 Task Chat 中，“继续”“取消”默认指向当前 Task；全局对话若没有唯一目标，先展示候选并请求指定，不按最近消息猜测高影响操作。新需求与当前任务是否相关不明确时，先澄清是否属于同一 Task。控制意图按动作与目标识别：只有明确指向 Task/执行/候选的暂停、取消、重试、验收等动作才进入控制路由；交付描述中的“停止计时”“重新开始”“等待人工验收”等说明仍按交付文本处理。

查询与闲聊不会重新打开已完成 Task，不会影响正在运行的计划。用户要求实际修改文件时，即使简单也创建或关联 Task/Run，保留 diff 与验收；不让直接回复路径绕过交付记录。反之，**仅上传/接入资料**是受控摄取作业，**不自动创建交付 Task/Run/团队**：在资料接入的授权范围内，程序可以直接写原件、资料记录、提取件与索引，**不要求工程交付 Run**，也不把每次上传变成重复确认门；但工程源码修改、Task 运行控制状态修改等仍遵现有 Task/Run 权限与验收，**摄取不能借机扩大授权**，有界工具问答仍只读。用户在同一请求里同时要求修改工程时，修改部分仍走 Task/Run 验收。资料接入、归属与检索的方向见 [资料接入与检索设计](09-source-intake-and-retrieval.md)（未实现、接口未冻结；具体处理状态/目录待接口冻结）。

## 3. 三条执行路径

1. **直接回复**：不调用工具，不创建团队。
2. **有界工具问答**：一个 agent，限制调用和时长，只读取获准数据或执行搜索；结束即释放。输出说明来源或实际调用结果，不承诺完成工程交付。
3. **交付执行**：Task/Run → 单 worker 或最小必要团队 → Subtask → 验证 → 候选交付 → 人工验收。独立 QA 可以顺序启动，不必与开发者同时驻留。

默认由程序按明确目标生成最小执行计划；可选的有界按需模型拆解提议只能作为候选，经程序校验后才落实预算与权限。不把“创建 Task”与“必须启动 swarm”绑定。路径升级时保存原因与已有输入；用户交付指令足够明确时自动执行获准工作，不为每次普通操作增加统一确认门。缺失输入和实际越出授权的动作才等待决定。

## 4. 全局对话与 Task 对话

全局入口需要最小会话记录，用于普通问答、任务选择和创建过程；不强迫每次闲聊创建 Task。候选存储为 `bot-data/conversations/<conversation-id>/messages.jsonl`。Task 创建后，其目标与相关输入写入 TASK.md/inputs，后续任务消息进入 Task 的 conversation.jsonl；全局历史保存 task_ref 导航，不复制整条 Task 对话。全局/Team 对话的状态查询按消息内**显式合法 Task ID**（`task_` 加 26 位 Crockford Base32）解析并读取持久状态快照，不依赖“最近/唯一活跃任务”猜测；缺失、非法、未知或出现多个不同 Task ID 时先澄清请求唯一目标，绝不任取第一个。该只读查询在 worker 忙时立即返回，不创建 Task/Run/worker，回复写入共享全局对话供所有登录成员查看；Team 的 Personal 私聊仍仅聊天且按身份隔离（LG-054）。该查询复用现有会话身份与 Task 权限，不新增角色、招募流程或执行预算。

团队模式下，Team 共享频道与 Task 对话使用同一 mention 判定：只有消息开头（允许前导空白）为配置的 bot mention（默认 `@bot`，后接空白、标点或结束）时才去除前缀并进入分类/机器人路由；未 mention 的普通消息只持久化，不调用分类器、responder/模型，不创建 Task/Run，也不写入 assistant 回复。单用户模式不要求 mention，Task 对话沿用原路由；带 `resource_proposal` 的结构化受控写入仍按资源提案权限处理，不受普通文本 mention 门影响。

消息至少记录 `messageId`、角色、时间、内容/附件引用、Task 关联和 correlationId。客户端重试发送相同 messageId 时幂等返回，不重复建 Task/执行。SDK 工具事件、成员会话在 Run 详情展示，主聊天以问题、决定、里程碑和交付为主。

上下文读取顺序：当前请求 → TASK.md 与版本 → 待决项 → 近期任务对话 → 当前 Run 摘要与相关证据 → 必要的 Project/资源引用。长期上下文来自文件，不依赖常驻模型记忆。压缩摘要是派生上下文，不能替代原始决定和消息。

## 5. 队列与执行期间消息

首版每个 Bot 实例同时只运行一个占用执行槽的交付 Run，多个 Task 可以排队。待用户、待验收、失败、已取消的已停止运行不占执行槽。后台协调器仍能回答状态与接收控制操作。

队列顺序保存在 Task 的 frontmatter `queue` 字段，不再维护另一份权威任务队列；索引按 order/queued_at 计算队列。领取时通过锁、版本和 owner/lease 记录保证一个任务不会被重复执行。任务依赖未满足时不领取；首版使用确定顺序，不扩展复杂优先级算法。

执行中：

- 状态查询读取快照立即返回，不排在代码任务之后；补充模型说明如需要也受全局请求额度限制。
- 新的独立交付需求加入队列，并告知排队位置；不会自动取消旧工作。
- 需求变更记录变更请求，先暂停新派发并与活跃 worker 协调停止/检查，再更新计划版本；不在 worker 写入期间悄悄替换验收条件。
- 暂停保留恢复点，取消终止本次工作；二者都必须确认实际执行已停止。
- “批准”“验收”必须关联具体 request/交付版本，重复提交幂等，过期回复不作用于新版本。验收/拒绝控件只在当前候选来自当前 Run、已完成验证并处于待验收、需求/交付版本与计划哈希一致且机器检查满足时可用；该交互门不替代服务端校验。

用户等待结束后恢复的 Task 重新进入执行队列，不抢占其他活跃任务。一个 Task 同时最多一个非终止的 Run；执行尝试恢复不能另起第二个 writer。失败或取消的已启动 Run 保留为历史；清理活动指针时仍保留 `last_run`，重试创建同一 Task 的新 Run 并使 attempt 递增，不从旧失败会话静默续接。共享仓库的 write lock 在 worker 完全停止后释放；其他任务开始前仍核对候选基准与未交付变更。

## 6. 状态渲染与统计

`status` 保留 `todo/in-progress/done`，`phase` 表达细节。展示和活动统计不能只检查 status。阶段与状态必须经过 schema 的合法组合校验，禁止 `done + executing` 等组合。

| 用户看见的状态 | 持久字段依据 | 执行槽 |
|---|---|---|
| 待补充 | phase=intake/waiting_user，附明确问题 | 无，确认停止后 |
| 排队／等待依赖 | phase=queued/waiting_dependencies | 无 |
| 规划、组队、执行、验证、返修 | 对应 phase，活跃 owner/lease | 有 |
| 正在暂停／取消 | phase=pausing/cancelling | 保留直到确认停止 |
| 已暂停 | phase=paused | 无 |
| 待验收 | phase=awaiting_acceptance | 无 |
| 失败／需检查恢复 | phase=failed/recovery_required | 没有活进程时无；未知进程必须先检查 |
| 已取消 | phase=cancelled | 无 |
| 已完成 | status=done，phase=completed，验收绑定当前交付 | 无 |

未执行的 Task 取消可以保持 todo，已启动失败/取消保持 in-progress；Board 根据 phase 放入失败/取消分组，不能显示成仍在运行。归档字段独立于完成，等待时间与执行时间分别统计。cleanup 状态独立显示，清理异常时不能谎报“所有资源已释放”。

## 7. 用户决策与资源释放

需要用户信息或实际批准时保存待决项 ID、Task/Run、请求内容、相关操作/计划版本和有效状态。回复先持久记录，再幂等回传；重复或过期回复给出明确说明。等待无回复不能视为批准。

进入待验收时先完成验证、保存候选版本和证据，停止并关闭空闲 worker、MCP 子进程与 session triggers，再交付待验收包。团队的配置与历史保留为已释放记录。人工验收不需要让队伍占用资源等待。

等待执行中的工具确认时，可在配置的短期限内保留受控 session；到期保存等待记录并停止。恢复是否重建会话取决于 SDK 已验证能力；不能假装已经执行过被拒绝或尚未批准的工具。

验收通过后 Task 置为 done；拒绝验收时保存具体问题与交付版本，创建同一 Task 的返修 Run，再按需组队。重新打开已完成 Task 增加需求/交付版本，旧证据保留。

“验收”表示用户接受候选产物，不自动合并代码、部署或发布。最终交付明确是文件、diff、候选提交还是预览链接；外部动作只有在本次任务授权范围内才能执行。

## 8. 断线、通知与服务恢复

浏览器关闭或连接断开不取消后台任务。持久 worker/协调服务继续执行；这种行为依赖常驻后端，不把网页请求进程视为长期 worker。日志写入文件后再广播，重连按事件游标补齐，不只依赖内存流。

完成、失败、预算停止、等待用户与待验收生成持久 Bot 通知记录（`bot-data/notifications/<notification-id>.md`），引用 Task 和事件 ID。该记录只维护已读/送达，不复制 Task 状态。首版提供网页通知列表和未读标记，用户离线时保留；邮件/Telegram/Slack 推送暂缓，不能宣称关闭网页后仍收到外部推送。

服务重启扫描队列、活动租约、待决项和未读通知。确定未开始的任务可继续排队；执行中断先检查进程、产物和副作用，必要时进入 recovery_required。SDK session 能否恢复按固定版本实测，不能仅凭聊天历史重新执行并宣称无损恢复。

## 9. 首次启动与部署范围

首版支持单用户本地网页使用。启动检查配置目录、文件权限、模型认证、平台 runtime、工具/隔离环境与必要资源 schema；区分致命故障与只影响可选能力的故障。模型或 worker 不可用时仍可浏览资料和历史，明确告知执行不可用，不假装开始运行。

缺模型连接/默认时提供底部 Settings 的配置入口。模型接入与秘密输入不经过普通 Chat；Settings 与 Connections 共用配置，首版先接通已验收的 OpenAI-compatible（`LocalOpenAIAgentConfig`）→ DeepSeek 路径。详见 [模型设置](07-settings-and-models.md)。

常驻服务候选使用单 Python 进程承接 API/协调队列，独立子进程或已验证隔离环境运行 SDK worker；持久数据在明确配置目录。入口、队列与 worker 生命周期在浏览器请求之外。网页框架与进程管理方式待实现选择，先避免引入分布式调度。

默认只监听 loopback，不提供无需认证的公网执行入口。若做云端演示，收敛为有访问控制的单用户部署、持久文件与长期 worker，另行确定认证和托管方式；不在首版引入组织、多租户或跨设备同步。凭证配置只保存引用，不写入任务对话或项目文件。

## 10. Bot 端到端验收场景

| 场景 | 必须观察到的行为 |
|---|---|
| “你能做什么？” | 直接回复，不建 Task、不组队 |
| “读这个文件，解释一下” | 获准只读工具回答并给来源，结束释放 session |
| “修改示例页面并验证” | 创建 Task/Run，单 worker 或按需团队，留下 diff 与 QA |
| 执行时问“进度如何？” | 读取真实状态回复，不等任务结束 |
| 执行时发送另一项需求 | 保存新 Task 并排队，不重复派发旧任务 |
| 执行时修改需求 | 可观察的暂停/版本修订，旧验收不用于新版本 |
| 用户重复发送同一请求 | messageId 去重，不生成第二个 Task/Run |
| “暂停”后“继续” | 确认停止、保留成果、按队列恢复，不产生双 writer |
| “取消” | 停止确认后显示 cancelled，保留成果与事件 |
| 浏览器断线后重连 | 后台继续，消息与日志按游标补齐 |
| QA 完成但用户未验收 | 释放执行资源，显示待验收，其他 Task 可以执行 |
| 用户拒绝交付后返修 | 同一 Task 新尝试，旧交付保留，按需重新组队 |
| 服务执行途中重启 | 检查并显示恢复结论，不自动重放不确定副作用 |
| 缺模型认证启动 | 可浏览历史，执行前明确说明故障，不伪造运行状态 |

上述场景与 SDK 探针一起构成首版验收，不要求先建外部 bot 渠道或自主后台触发。
