### 产物（仅本任务归属）

- `backend/lightgravity/verify/candidate.py`：`Candidate` 候选快照与 `load_candidate`。
  从权威 frontmatter 读取 Task 的 `requirements_revision`/`deliverable_revision`、Run 的 `state`/`plan_hash`/`team_refs`/`subtask_refs`/`session_refs`，
  聚合 Subtask `acceptance.evidence_refs` 为候选证据；只读，不执行资源、不 eval/import Markdown。
- `backend/lightgravity/verify/checks.py`：进程内 `CheckRegistry` / `CheckRegistration` / `CheckContext` / `CheckReport` / `run_checks`。
  仅运行“程序已注册且 Task 授权”的检查；未注册的授权检查记为 `unconfigured`（不运行），处理器异常记为 `error`（绝不当通过）。
  默认注册 `evidence-present`（必须存在真实产物/diff 证据，worker 摘要不算证据）与 `artifacts-in-workspace`（工作区内相对路径必须存在且不越界）。
- `backend/lightgravity/verify/stopgate.py`：`ResourceStopper` 协议 + 默认 `StoreResourceStopper`。
  依据 Store 权威状态确认：Run 不在 `planning/recruiting/executing/pausing/cancelling`；会话关闭（无 session 或 `cleanup.status=done`）；
  仅在确认停止后释放非终态 Member 为 `released`；释放 Task 执行槽租约（必要时 `Store.release`）。未确认停止绝不假释放。
- `backend/lightgravity/verify/service.py`：`VerificationService`（`verify_and_prepare` / `decide` / `request_repair` / `acceptance`）。
  机器检查 → 停止/释放门 → 候选进入 `awaiting_acceptance`（`deliverable_revision + 1`，写入绑定版本的 `acceptance` 与 `decision.requested` 事件）；
  accept/reject 绑定 `requirements_revision` + `deliverable_revision` + `candidate_ref`/`candidate_plan_hash`，按 `request_id` 幂等，过期/跨候选回复 `acceptance_stale`，
  不自动 merge/push/deploy。所有控制状态经 `coordinator.state.StateWriter`（→ `Store`）写入，保留正文与未知字段；worker 不写控制。
- `backend/lightgravity/verify/router.py`：独立 `build_router(service)`，暴露 `GET /tasks/{task_id}/acceptance` 与 `POST /tasks/{task_id}/actions`（accept/reject）。
  自行把 `AppError` 转为冻结错误信封；**未**改 `api/app.py`、coordinator、adapter、Store、contracts。
- `backend/lightgravity/verify/README.md`：最小接线说明。

### 诚实说明与限制

- **检查范围**：机器检查是进程内已注册的最小型集合，且必须由 Task 的加性 `checks` 字段授权。若 Task 未声明 `checks`，则不运行任何机器检查（如实显示为空），不会把无检查当作通过；授权但未注册的检查记为 `unconfigured` 且不运行。未实现通用/动态插件式检查平台。
- **停止确认**：默认 `StoreResourceStopper` 依据权威状态判断 Run 停止、会话关闭与槽位释放；verify 不持有 executor，真实 SDK 会话关闭的更强确认由 LG-010/LG-016 注入 `ResourceStopper` 端口。执行中（Run 活动）绝不释放成员或写终态。
- **返修**：`request_repair` 与 reject 只把 Task 置 `repairing`（保留 Task ID）、把当前 Run 置终态；不创建新 Run、不做多轮 QA 编排（LG-017）。重复决策幂等；并发同 `request_id` 的极端竞态未做分布式互斥（文件级幂等，原型范围）。
- **候选证据**：`check_records` 目前从 Subtask 的可选字段读取，LG-008 未持久化 `ExecutorResult.check_records`；候选 diff 由以 `.diff`/`.patch` 结尾的证据引用识别。更完整的产物/证据索引由 LG-014 覆盖。
- 本记录是执行者局部证据，**待版本 QA**；未做真实模型调用、未 push/deploy、未启动产品服务。
