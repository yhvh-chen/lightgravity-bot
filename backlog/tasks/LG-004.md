# LG-004 — 实现 Markdown 事实源与可靠写入

## 目标

实现实体解析、版本化持久写入、消息事件和可重建索引。

## 范围

阶段：基础与探针。仅实施本项所需首版能力；不扩展多后端、组织、云端或外部渠道。

## 验收条件

- 无效 YAML、重复键/ID、非法状态、路径越界有诊断，保留正文与未知字段。
- 冲突、锁/租约、原子替换和部分写入恢复有故障注入证据。
- 无第二份当前状态事实源，消息幂等与索引重建有效。

## 依赖

LG-001、LG-002 为接口或实际交付需要，不是单纯阶段排序。

## 交付物

新增包 `backend/lightgravity/store/`（仅 LG-004 owner 路径）：

- `frontmatter.py`：ruamel round-trip 解析，拒绝重复键，保留正文/未知字段/键序；`merge_maps` 深合并保留未知扩展字段。
- `entities.py`：`lightgravity.bot/v1` schema/kind/id/revision 校验；Task `status+phase` 合法组合表与迁移表（docs/08 §6.1），Run/Subtask/Member/资源静态校验；冻结事件类型集合。
- `paths.py`：`resolve_workspace_path` 拒绝 `..`、越界绝对路径与符号链接 realpath 逃逸（docs/08 §10）。
- `locking.py`：基于 `fcntl.flock` 的跨进程/跨线程实体内锁，超时抛 `LockConflict`。
- `atomic.py`：同目录临时文件 + `fsync` + `os.replace` + 目录 `fsync`；JSONL 追加 + `fsync`；不完整/尾部损坏行截断恢复。
- `events.py` / `messages.py`：事件流 `seq` 在流锁内单调无空洞；消息以 `message_id` 幂等。
- `index.py`：可重建派生索引，扫描权威文件并报告非法实体与重复 ID。
- `protocol.py`：docs/08 §7 的 `Store` Protocol；`store.py` 的 `FileStore` 为其实现。
- `errors.py` / `models.py` / `ids.py` / `clock.py`：契约错误码子类、记录类型、ULID、可注入时钟。

新增测试 `tests/store/`（仅 LG-004 owner 路径）：解析/校验/路径/实体/日志/租约/恢复/真实跨进程并发共 69 项。

未修改：根 `pyproject.toml`、`uv.lock`、`backend/lightgravity/contracts/**`、`backend/lightgravity/api/**`、`frontend/**`、其它任务文件、`PROJECT.md`、`README.md`、`agent.md`、共享契约。

验收条件对应证据：

- **诊断与保留**：`tests/store/test_frontmatter.py`、`test_validation.py`、`test_paths.py`。重复键 → `duplicate_key`；非法 YAML → `invalid_yaml`；非法 `status+phase`（如 `done+executing`）→ `illegal_status_phase`；非法迁移（`planning→executing`）→ `illegal_transition` 且不落盘；重复 ID → `duplicate_id`；`../`、越界绝对路径、`/tmp` 符号链接逃逸 → `PathOutsideWorkspace`（403 码）。写入后未知字段 `extension_field`、正文、键序保留。
- **冲突/锁/租约/原子/恢复（故障注入）**：`test_entities.py` revision 冲突报 `expected/actual/etag` 且不覆盖新值；`test_leases.py` 活跃租约拒绝他人 `claim`、过期可接管、错误 owner `release` 抛 `LockConflict`；`test_recovery.py` 注入残留 `.lg-tmp-*` 与不完整 JSONL 行，`recover()` 删除临时文件、截断到最后完整记录并写 `error.recorded`，后续追加序号连续。
- **真实并发写**：`test_concurrency.py` 以 `subprocess` 启动独立进程。4 进程 × 20 事件 → 事件 `seq` 恰为 1..80 无空洞、JSONL 无坏行；4 进程竞争 `claim` → 恰 1 `CLAIMED`、3 `LOCKED`；4 进程同 `expected_revision=0` 写 → 恰 1 `WROTE`、3 `CONFLICT`，revision=1；4 进程同 `message_id` 追加 → 4 次成功但仅 1 条记录。
- **单一事实源与索引**：状态只在 TASK.md/RUN.md 等权威 frontmatter；`rebuild_index()` 从文件扫描重建，内存索引可丢弃后重建（`test_logs.py`），非法实体/重复 ID 只报诊断不入索引。

失败与处理：首轮 `uv run mypy` 报 14 处类型错误（Any 收窄、事件 `type` 联合），已按实际类型修正后复跑通过；无行为失败残留。

耗时：实现与迭代未逐段计时；测试墙钟 `pytest tests/store -q` 约 1.5s（含并发子进程）。成本/token：不可得，记为未知。

限制与待整合：

- 事件与消息采用 store 内部布局 `events/<stream_id>/events.jsonl`、`tasks/<task_id>/conversation.jsonl`；docs/02 的运行目录嵌套是候选约定，Store API 不暴露路径，故未视为契约变更。运行时实体（run/subtask/member）使用扁平容器以支持 `read(kind, id)` 单键解析，引用仍由 `task_ref`/`run_ref` 关联。
- 锁为单主机 `flock`；docs/08 §2.1 首版即单进程模型，未实现分布式锁。
- `claim` 复用 Task 写路径，租约通过 `queue` 字段与 revision 一并持久化，不新增租约文件。
- 未改动 `backend/lightgravity/api`；HTTP/SSE 接线由 LG-012 基于 `Store` Protocol 完成，本任务只交付 store 层。`resolve_path` 已可供 LG-014 文件树使用。
- 无新增共享依赖或契约变更需求：`ruamel.yaml` 已在 LG-002 根依赖中；未修改禁写路径。
- 本成果标注“待版本 QA”，未声称版本验收通过。
