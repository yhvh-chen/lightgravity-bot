### 问题（阻断 LG-010）

1. **高 / 阻断** `artifacts-in-workspace` 把 executor 的绝对 `diff_ref` 当作工作区相对路径。
   - 文件：`backend/lightgravity/verify/checks.py`（`artifact_path` / `_artifacts_in_workspace`）；交互方 `backend/lightgravity/coordinator/graph.py::_apply_result` 将 `result.diff_ref` 追加进 Subtask 证据，`backend/lightgravity/adapter/executor.py` 用 `DirectoryArtifactSink` 返回绝对路径。
   - 复现：`probes/lg010/evidence/lg010-evidence.json`（`verify.state=unconfirmed`、`artifacts-in-workspace failed: outside workspace`）与 `probes/lg010/evidence/lg010-check-repro.json`（带绝对 ref 失败、不带通过）。
   - 影响：授权默认检查后候选无法进入 `awaiting_acceptance`，停止/释放门不运行，accept/reject 不可达；人工验收缺失。
2. **高 / 阻断** Coordinator 成功后未调用 `VerificationService.verify_and_prepare`，且没有触发验证的 HTTP 端点。
   - 文件：`backend/lightgravity/coordinator/service.py`（`_apply_outcome` 进入 `verifying` 后无验证调用）、`backend/lightgravity/api/app.py`（无 verify 路由）。
   - 影响：用户从 HTTP 交付入口到 `verifying` 后无法到达 `awaiting_acceptance`；PROJECT.md 已把该接线交给 LG-010，当前缺失。QA 期间由 harness 直接调用 `app.state.verification.verify_and_prepare` 继续后续步骤。

### 返修 1：统一 artifact 引用/解析语义（problem 1）

- 新增 `backend/lightgravity/evidence.py`：把可信 executor 产物导入 `<data_dir>/tasks/<task_id>/artifacts/<run_id>/`，记录 `evidence:<run_id>/<name>@sha256:<hex>`；`resolve_evidence_ref` 校验 Task 归属（root）、Run 归属（run_id 分量）、路径/符号链接包含与内容摘要。
- `backend/lightgravity/verify/checks.py`：`classify_artifact_ref` 明确 workspace/evidence/absolute/opaque 四类；workspace 引用按授权 workspace 根解析，evidence 引用按 store data_dir 的 Task/Run evidence 根解析；`absolute` 直接失败，`opaque` 跳过。
- `backend/lightgravity/coordinator/graph.py::_apply_result` 在写入 Subtask `evidence_refs` 前调用 `import_evidence`；不可读时按 `evidence_unreadable` 诚实失败。`backend/lightgravity/verify/candidate.py` 按解析后的名字识别 diff/patch。
- 安全边界：check 只读 store 拥有的 Task/Run evidence 根与授权 workspace 根；原始绝对路径、跨 Task、跨 Run、越界/符号链接、摘要不符均拒绝；未放宽为任意绝对文件可读；未删除 `diff_ref`、未跳过检查。
- 回归：`tests/verify/test_verify_checks.py::test_artifacts_check_resolves_canonical_evidence`（canonical 通过、跨 Run 拒绝、原始绝对路径拒绝、摘要篡改拒绝）；`tests/coordinator/test_graph_dispatcher.py::test_executor_diff_ref_is_canonicalized_into_task_evidence`（记录为 canonical、绝对路径不再出现、check 通过、篡改检出）；`tests/verify/test_verify_service.py::test_verify_prepares_candidate_with_canonical_evidence`（经 app 的 broadcasting store 走完整 `verify_and_prepare` 到 `awaiting_acceptance`）。

### 返修 2：交付完成后自动验证（problem 2）

- `backend/lightgravity/coordinator/service.py` 新增结构化 `CandidateVerifier` 端口；`_apply_outcome` 在成功 Run 写为 `verifying` 后自动调用 `VerificationService.verify_and_prepare`（request_id `auto-verify:<run_id>`），由真实 `StoreResourceStopper` 执行停止/释放门；失败只记录 `error.recorded` 并保持 `verifying`，不伪造验收。
- `backend/lightgravity/api/app.py` 先构建 `VerificationService`，再构建默认 `Coordinator`；并对**显式注入的 coordinator** 调用 `set_verification` 回挂同一服务，因此 `create_app(..., coordinator=..., dispatcher=..., executor=...)` 路径同样自动验证。
- 未新增隐藏 HTTP 端点；accept/reject 仍走既有 `POST /tasks/{task_id}/actions`。
- 回归：`tests/api/test_integration_wiring.py::test_injected_coordinator_auto_verifies`（显式注入 coordinator/dispatcher/executor 经真实 API 到 `awaiting_acceptance` 并读到 acceptance 快照）；`tests/api/test_events.py` 断线续跑用例更新为断言自动到达 `awaiting_acceptance`。
